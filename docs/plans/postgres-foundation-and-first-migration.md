# PostgreSQL foundation and first migration plan

## Goal

Create a reproducible local PostgreSQL development setup and a migration
workflow for the FastAPI service. The first migration will establish the
identity and household tenancy foundation without implementing authentication
endpoints or product features.

## Scope

1. Add a local-only PostgreSQL Docker Compose service named `postgres`, with a named data volume,
   health check, localhost-only port binding, and no committed credentials.
   Document the environment variables each developer supplies locally.
2. Add Alembic and the Psycopg PostgreSQL driver to the API's Python
   dependencies. Use handwritten Alembic migrations containing explicit SQL;
   do not add an ORM or use Alembic autogeneration in this feature.
3. Add a small API configuration module that reads `DATABASE_URL` only when
   Alembic needs it. It is an Alembic/SQLAlchemy
   `postgresql+psycopg://` URL; defer direct Psycopg application connection
   configuration until database-backed API work begins. Keep `/v1/health`
   independent of a live database; a database-backed readiness endpoint is
   outside this change.
4. Configure Alembic with migration scripts in the repository-level
   `db/migrations/` directory, matching the intended project structure.
5. Create a first Alembic revision conceptually named
   `identity_and_households` (Alembic generates its revision ID) with:
   - `users`: UUID key, identity provider and subject, normalized email,
     display name, audit timestamps, and deletion fields consistent with the
     email-reuse policy.
   - `households`: UUID key, name, IANA time-zone value, creator audit field,
     timestamps, and deletion field.
   - `household_members`: UUID key, household/user foreign keys, `owner` or
     `member` role, joined/removed timestamps, and unique membership.
   - `household_invitations`: UUID key, household foreign key, normalized email,
     token digest, invitation role/status, expiry/lifecycle timestamps, and a
     partial unique index for one pending invitation per household/email.
   - Required partial unique indexes, check constraints, UUID defaults using
     `DEFAULT gen_random_uuid()`, and explicit foreign-key delete actions.
6. Document commands to start PostgreSQL, apply the migration, inspect the
   migration state, and reset only the explicitly named disposable test
   database.
7. Add migration-focused tests or a repeatable verification command that proves
   a fresh database can migrate to `head` and exposes the expected constraints.

## Important decisions

- Use PostgreSQL UUID values generated by the database with
  `DEFAULT gen_random_uuid()`. Do not add a UUID extension in this migration.
  This keeps IDs available for direct SQL and future workers without relying on
  API-only ID generation.
- The first migration stores `identity_provider` and `identity_subject` and
  makes that pair unique. A subject alone is globally unique only if the future
  identity provider explicitly guarantees it; no provider has been selected, so
  the schema must not assume that guarantee.
- Store normalized email as text and normalize at the application boundary;
  avoid a second case-insensitive extension for the first migration. Use a
  partial unique index on `normalized_email WHERE deleted_at IS NULL`. Account
  deletion later anonymizes/releases the email according to the approved policy.
  The migration also enforces
  `normalized_email = lower(btrim(normalized_email))`.
- Validate IANA time-zone membership in application configuration/service code;
  the first migration will still require a nonblank value because a PostgreSQL
  `CHECK` constraint cannot directly query the time-zone catalog.
- Keep invitation expiry as service behavior. The database records `status` and
  `expires_at`, while a creation transaction marks stale pending invitations
  expired before enforcing the pending-invitation unique index.
- `household_members` uses a partial unique index on
  `(household_id, user_id) WHERE removed_at IS NULL`, allowing preserved history
  and a later rejoin. `household_invitations` similarly uses a partial unique
  index on `(household_id, normalized_email) WHERE status = 'pending'`.
- Use `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` for `created_at` and
  `updated_at` on durable mutable records. The service explicitly advances
  `updated_at`; this first migration adds no implicit update trigger.
- Use `ON DELETE RESTRICT` for the initial identity and household foreign keys.
  Account and household deletion are intentional workflows, not cascades.
- Constrain member and invitation roles to `owner` / `member`, and invitation
  status to `pending` / `accepted` / `revoked` / `expired`, with appropriate
  nonblank checks for names, normalized emails, and time-zone values.
- Defer the "at least one active household owner" invariant to the future
  membership-management service transaction and its tests; a simple row-level
  database constraint cannot safely enforce it.
- Defer parent `UNIQUE (household_id, id)` constraints until a child table
  actually needs a composite foreign key. Add that parent constraint and its
  child foreign key together in the same later migration.
- Do not add an authentication vendor, user registration/login routes,
  PostgreSQL row-level security, recipe/list tables, cloud hosting, or a
  committed `.env` file in this feature.

## Validation

Alembic configuration lives at `services/api/alembic.ini`; its `script_location`
points to the repository-level `db/migrations/` directory. From the repository
root, start the local database with `docker compose up -d postgres`. Then run
these commands from `services/api`:

1. `uv run alembic -c alembic.ini revision -m "identity and households"` to
   create the revision file; write its `upgrade` and `downgrade` SQL by hand and
   do not pass `--autogenerate`.
2. `uv run alembic -c alembic.ini upgrade head`
3. `uv run alembic -c alembic.ini current --check-heads`
4. `uv run alembic -c alembic.ini history`
5. Run `uv run pytest` and `uv run ruff check .` to confirm the API foundation
   remains healthy.
6. Run `git diff --check` before review and commit.

Reset verification is allowed only against the explicitly named disposable
database `meal_planner_disposable_test`, never the development database. Its
verification procedure drops/recreates that database, sets `DATABASE_URL` to
that database, then runs the `upgrade head` and `current --check-heads`
commands above. The implementation will not run that destructive reset without
first confirming the resolved target is exactly that disposable database.

Migration-level tests must verify a fresh migration and the constraints below:

- UUID defaults, required timestamp defaults, and the absence of an implicit
  `updated_at` update trigger.
- `ON DELETE RESTRICT` behavior for user/household membership and invitation
  relationships.
- Allowed and rejected member roles and invitation statuses.
- Active-email, active-membership, and pending-invitation partial uniqueness;
  a deleted user, removed membership, or non-pending invitation must no longer
  conflict.
- Required nonblank names and household time-zone values, plus the normalized
  email lower-and-trim canonicalization check.

## Review points

- Confirm the proposed handwritten Alembic + Psycopg toolchain, without an ORM
  or migration autogeneration.
- Confirm the first migration is intentionally limited to users, households,
  memberships, and invitations; catalog/recipes/planning/shopping follow in
  later migrations.
- Confirm Docker Compose is the desired local PostgreSQL path. No cloud database
  or provider selection is included.
