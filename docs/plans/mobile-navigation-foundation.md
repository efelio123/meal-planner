# Signed-in mobile navigation foundation plan

Status: draft for review; no implementation is approved yet.

## Goal and scope

Add the signed-in bottom-navigation foundation with exactly five tabs, ordered Plan, Recipes, Shopping, Pantry, Settings. Plan is the permanent product startup tab. While Plan is only a placeholder, Shopping is the temporary startup destination. Keep the selected startup route centralized so changing it to Plan later is a small, clear change rather than duplicated platform configuration. Plan, Recipes, and Pantry are simple themed, accessible “Coming soon” pages only—no fake data, inactive controls, or placeholder product behavior. Settings is the future home for account and household management; this slice moves sign-out there and shows the currently selected household. Authentication, household onboarding/selection, and API-retry screens remain outside the signed-in tab navigator.

No invitation implementation, recipe/planning/pantry functionality, new API endpoints, database changes, deep links, or provider changes are included. The three “Coming soon” routes must not imply that those product features exist. The owner-invitation plan remains an unapproved draft; it must later be revised so its owner entry point and screen live within Settings, retain code-only manual sharing, and continue deferring invitation URLs/deep-link routing to a separately approved plan.

## Proposed route architecture

Keep the current root stack and its signed-out, onboarding, API-error, and signed-in guards. Keep `(auth)`, `(onboarding)`, and `(api-error)` as root-level sibling groups, never children of the signed-in tabs. Within the already-protected `(app)` group, add a tab group and give every tab its own route folder and nested stack:

```text
src/app/
  _layout.tsx                 root auth/household guards and stack
  (auth)/                     signed-out screens; outside tabs
  (onboarding)/               create/join/select; outside tabs
  (api-error)/                retry/sign-out; outside tabs
  (app)/
    _layout.tsx               signed-in stack containing the tab group
    (tabs)/
      _layout.native.tsx      five native tabs for iOS/Android
      _layout.tsx             five JavaScript tabs for web
      plan/_layout.tsx        Plan stack
      plan/index.tsx          accessible themed Coming soon page
      recipes/_layout.tsx     Recipes stack
      recipes/index.tsx       accessible themed Coming soon page
      shopping/_layout.tsx    Shopping stack
      shopping/index.tsx      existing shared shopping-list screen
      pantry/_layout.tsx      Pantry stack
      pantry/index.tsx        accessible themed Coming soon page
      settings/_layout.tsx    Settings stack
      settings/index.tsx      Settings home
```

Move `src/app/(app)/index.tsx` to `src/app/(app)/(tabs)/shopping/index.tsx` without changing its shopping behavior. Move only shopping-specific support code out of shared locations: `src/hooks/use-shopping-list.ts` and its hook test to `src/features/shopping-list/`, and move `src/__tests__/shopping-list.test.tsx` to `src/features/shopping-list/`. Update feature imports and test paths. Keep the shopping route screen in `src/app/` because it is a route; keep the app-wide `use-household-state` hook in `src/hooks/`, the shared `SignOutAction` in `src/components/`, and `src/lib/api.ts` and its API-client tests in `src/lib/`. Keep `src/__tests__/app-route-test-placement.test.js` as an app-wide guard, and expand it if needed to enforce the organization rule. Do not reorganize auth/onboarding files or other unrelated code. Add the Settings and three simple placeholder route screens, but create no feature-support folders for them unless supporting logic is actually needed.

Expose exactly five tabs in this visual order: Plan, Recipes, Shopping, Pantry, Settings. Explicitly declare native triggers and web tab screens; keep `(tabs)` free of any other direct route files/folders that could become an accidental tab. Keep that trigger/screen order unchanged. Store the signed-in startup target in one navigation feature helper/constant under `src/features/navigation/`, consumed by the root dispatcher; set it to the explicit full Shopping route during this slice. Plan remains the permanent default product destination, and changing the temporary target to Plan later should require changing that one centralized value once Plan is implemented. On SDK 57 NativeTabs, do not rely on `unstable_settings.initialRouteName`: the installed-version implementation does not pass that setting into its tab router, so a cold start without a route path can select the first trigger (Plan). Instead, have the root dispatcher replace `/` with the centralized explicit route after auth/household resolution. Test that temporary Shopping redirect in the actual SDK 57 router on cold startup and after onboarding. Keep the group path valid if typed-route generation chooses a different canonical href. Do not add custom navigator workarounds or change architecture solely to accommodate the temporary Shopping default. If the route redirect is unreliable, pause and present supported alternatives for approval—including making Plan the default earlier, using JavaScript Tabs on all platforms, or revisiting after a separately approved Router upgrade.

When an onboarding operation changes household state to `app`, make sure the route guard/index dispatcher lands on the centralized temporary startup target (Shopping in this slice). Keep auth, onboarding, and API-error screens as root siblings outside all signed-in tabs. In SDK 57, use the always-accessible root `index` dispatcher as the explicit fallback/anchor and keep it explicitly registered first in the root stack; it directs by current auth and household destination to sign-in, create/join, select-household, API-error, or the selected startup target. Do not rely on alphabetical file order or on SDK 58's `redirectTo` feature, which is not available in this installed SDK. Test the actual redirect and protected-route history behavior.

Header ownership: root and `(app)` container stacks have no visible header; the tab bar has labels/icons but no screen header. Each tab has a nested `Stack` so future child screens get native stack Back behavior. For the five tab-root routes, hide the nested stack header and let the screen content own one accessible title; future child routes use the nested stack header and must not repeat the same title in their content. This avoids duplicate parent, tab, and screen headers while retaining a Back button for pushed child routes.

## Navigator choice and dependency decision

Recommendation: use Expo Router Native Tabs on iOS and Android, and the existing JavaScript `<Tabs>` navigator on web through the platform-specific layout files shown above. The app's primary targets are native phones, the confirmed product direction has five stable peer destinations, and both Apple and Android guidance supports a labeled native tab/navigation bar at this count. Native tabs offer the strongest native platform experience and platform-specific icon support. A small web-only JavaScript fallback avoids relying on a native navigator on web while keeping the same route tree/screens.

SDK 57 exposes native tabs as `NativeTabs` from `expo-router/unstable-native-tabs`; the API is therefore not yet stable. SDK 57's currently recommended Expo Router patch is `57.0.23`, versus this lockfile's `57.0.18`. Expo Symbols is already present at `57.0.2`, and the SDK 57 docs recommend `57.0.3`. Proposed dependency changes for approval are:

- `expo-router`: update the package range/resolution from `~57.0.18` / `57.0.18` to `~57.0.23` / `57.0.23`.
- `expo-symbols`: update from `~57.0.2` / `57.0.2` to `~57.0.3` / `57.0.3` for the SDK-aligned SF Symbols/Material Symbols API.
- Keep Expo at `57.0.19`, React Native at `0.86.3`, React at `19.2.3`, `react-native-screens` at `4.26.2`, and `react-native-safe-area-context` at `5.7.0`. Add no packages; these are patch-level Expo SDK 57-compatible updates. Do not apply them before plan approval.

JavaScript tabs remain the alternative for all platforms: their API is the established Expo Router/React Navigation option, is flexible, and avoids platform-specific layout files or an unstable tab API. The tradeoff is that the bar is rendered by the JavaScript navigator, not each platform's system tab control, and its interaction details may feel less native. Replacing NativeTabs with JavaScript tabs later is moderate migration work: keep route screens/stacks, but rewrite the tab layout options, icons, styling, and Back behavior and repeat all platform acceptance checks.

SDK 58 now exposes stable Native Tabs at `expo-router/native-tabs` (current documented Router version `~58.0.8`) and changes broader Router navigation behavior. It would otherwise be attractive for long-term native foundations, but the locked `@clerk/expo 4.6.5` declares `expo >=54 <58`; the current official Clerk Expo package metadata still excludes Expo 58. Do not upgrade Expo/React Native to SDK 58 or bypass that peer range. Revisit once Clerk officially supports SDK 58; that migration would be separate and include the Expo SDK 58 baseline (React Native `0.88`, React `19.3.0`), package alignment, Router 57→58 behavior changes, new native builds, and revalidation of auth/onboarding and protected-route fallback. The existing SDK57 native tabs path is the supported combination available to this project now, despite its unstable API label.

Native-tab limitations to plan around: tab definitions are static (which matches the fixed five-tab decision); SDK 57 native tabs eagerly render all five roots; each tab must explicitly own a nested Stack; and native platform behavior can differ from the web fallback. The lightweight placeholder roots are safe to eagerly render; Shopping's existing request behavior must still be tested for a single initial load. On Android, tab-bar/keyboard interaction must be verified: SDK 57 offers `tabBarRespectsIMEInsets`, requiring Android 11+ and keyboard layout mode `resize`; if not used, the keyboard may overlay the tab bar. Use NativeTabs' iOS SF Symbol and Android Material icon names; use the installed `expo-symbols` cross-platform API for the web JavaScript layout.

## UI, accessibility, and platform behavior

- Use existing semantic theme tokens for tab-bar surface, active and inactive icon/label tint, separators, screen backgrounds, and nested-stack headers. Verify mounted light/dark appearance updates without introducing separate theme state.
- Declare labels and accessible selected state for all five tabs. Use SF Symbols on iOS and Material Symbols on Android: calendar/list-plan, book/recipes, cart/shopping, pantry/storage, and gear/settings. Use semantic theme tokens for tab surfaces, active/inactive states, dividers, and route content; do not add manual theme state. The three Coming soon pages use the shared `Screen` and `ThemedText`, announce a page heading plus “Coming soon” to assistive technology, and contain no disabled buttons or mock content.
- Keep the selected household name and shared `SignOutAction` on Settings. The Settings screen can show the existing membership role if available, but this is informational only; do not add household switching, account editing, invitation, or other management behavior yet.
- Safe-area ownership is explicit so a route gets each inset exactly once. Keep one `SafeAreaProvider` at the app root. For iOS NativeTabs roots, SDK 57's Router sets `overrideScrollViewContentInsetAdjustmentBehavior` on each tab screen by default; `react-native-screens` changes the first descendant ScrollView from React Native's `never` to `automatic`. Therefore the tab-root `Screen` must use `contentInsetAdjustmentBehavior="automatic"` and apply no `SafeAreaView` edges on iOS, delegating top/side content insets to that scroll view adjustment and tab-bar clearance to the native tab/container. The shared content container must not add matching safe-area padding. Other (non-tab) iOS screens retain explicit `SafeAreaView` edges and `contentInsetAdjustmentBehavior="never"`. On Android, SDK 57 NativeTabs automatically wraps tab content in a safe-area view with only the bottom edge; shared `Screen` adds top and horizontal edges and uses `never`, while the native host owns bottom/tab-bar clearance. On web, the JavaScript tab navigator reserves tab-bar space; shared `Screen` applies top and horizontal browser safe-area edges once and omits bottom to avoid duplicating navigator clearance. Verify top cutouts, landscape side insets, tab-bar clearance, and bottom gesture/navigation areas on device/browser.
- Use existing shared `Screen`, `ThemedText`, and controls. Nested native stacks own navigation behavior, not duplicate safe-area padding. Keep shopping list controls reachable above the native tab bar, Android navigation system bar, and keyboard. Theme tab, stack, status/system bars from the existing palette in both modes and confirm a mounted appearance change updates the colors.
- Shopping focus/blur contract: native tabs eagerly render roots and tab routes may stay mounted. A tab switch is not a household or session change: preserve Shopping draft, list contents, scroll position, pending mutation state, and displayed errors. Valid responses from operations started in the same still-active household/session may update the Shopping state while another tab is focused or after returning, including successful loads/mutations, visible action errors, and optimistic rollback on a genuine same-household failure. A refresh concurrent with a mutation must not hide that mutation's valid result. Tab changes must not themselves trigger reloads, mutation retries, or focus-triggered `/v1/me`/shopping requests; explicit Refresh, initial mount/household load, and legitimate post-mutation authoritative refreshes remain allowed. Household or Clerk-session changes invalidate older requests: late loads, mutations, errors, and rollbacks from the old household/session must not change the new state. Do not unmount screens or use focus-conditional replacement. Avoid a useEffect dependency on unstable `getToken` identity; retain latest-token-ref and generation protections.
- Keyboard behavior: switching tabs dismisses the keyboard if necessary so navigation remains usable, but does not clear the shopping draft. Tapping away and returning must not resubmit or reset forms. On Android set SDK 57 NativeTabs `backBehavior="history"` and test it in the actual router. Back follows tab visit history; do not add a custom handler to force Settings back to Shopping. Back from a child first pops that tab's nested stack, and the keyboard gets its normal first dismissal behavior. At a tab root with no prior tab history, verify the normal app/OS exit behavior. Never route to onboarding or auth while Clerk remains signed in.
- Sign-out calls the existing shared household-state `signOut()` and does not implement custom session clearing. Existing guards must remove signed-in routes from navigation history after session invalidation. Back after sign-out must not restore a signed-in tab or Settings; a later sign-in starts a fresh selected household flow and Shopping tab state.
