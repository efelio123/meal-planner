## Goal and scope

Let an active household owner create a member invitation from Settings, see its expiration, and copy its one-time invitation code for manual sharing. Explain that the recipient must sign up or sign in with the invited email, then enter the code in the existing Join a household screen. The API remains authoritative for owner authorization, verified-email matching, seven-day expiry, and single-use acceptance.

This is a mobile/API-client code-only slice. Do not add invitation URLs or deep links, email delivery, Clerk Organizations, API/schema changes, cloud deployment, or persistence for invitation codes. Record links as a later follow-up: a shareable URL should open the app and preserve/prefill the code through authentication, but opening it must not accept the invitation. Link routing and behavior when the app is not installed require a separate approved plan.

## Existing contract and user flow

The existing API route is `POST /v1/households/{household_id}/invitations`, with `{ "email": "..." }`. It returns `{ "invitation": { "id", "expires_at", "code" } }`; the code is returned only at creation. The service accepts invitations only from active owners, always assigns the `member` role, normalizes the email, expires stale pending invitations transactionally, rejects a duplicate active invitation with `409`, and sets expiry to seven days. The existing join flow posts the raw code in the JSON body to `/v1/invitations/accept`; backend acceptance requires the signed-in user’s provider-verified normalized email to match and is single-use.

Proposed owner flow:

1. In the Settings home, show the current household and an “Invite a household member” action only when there is a selected household and its active membership role is `owner`. A member must not see or open the owner flow. Invitations do not appear on other tabs.
2. Open an invitation screen in the Settings nested stack. Collect and validate the recipient's email, then submit through the typed API client using the selected household ID and a fresh Clerk session token for that request.
3. On success, create one paired invitation snapshot containing the normalized email submitted for that request plus the returned invitation ID, raw code, and expiry timestamp. Display the recipient instruction, code, and expiry from that same snapshot, never from the editable email field.
4. If the owner gets `409`, explain that an active invitation already exists and its code cannot be retrieved by this request; use the code previously shared or wait until it expires. Do not suggest creating another invite or expose backend details.
5. The recipient manually enters the code in the existing onboarding-only Join a household screen and signs up/signs in with the invited email. This slice supports recipients who currently have no household; joining an additional household is outside scope. The server performs the final email, expiry, membership, and single-use checks.

## State, security, and error decisions

- The creation response’s raw code may exist only in component memory and the user-requested system clipboard. Never put it in AsyncStorage, logs, analytics, crash metadata, test output, or route/navigation params. Do not pass it to a share URL or analytics event. Clearing/unmounting the screen discards app-held code state; clipboard content is an explicit user action and is outside app-managed persistence.
- Treat route focus and route lifetime separately. A temporary tab switch only blurs the Settings tab; while the invitation route remains mounted in its nested stack, preserve its email draft, paired invitation snapshot, copy feedback, and pending request. Blur must not clear state, submit again, or create a request loop. When the invitation route is popped/closed or unmounted, clear its in-memory email/code/snapshot/feedback and invalidate pending creation/copy work. Do not tie cleanup merely to tab blur.
- Capture the selected household ID, Clerk user/session identity (or a monotonically increasing auth-session generation), active owner role, and a request generation when creation starts. Invalidate pending work synchronously when any captured identity changes, sign-out begins, owner access is lost, the route closes, or it unmounts. Household/session/access changes clear the old code/expiry snapshot. A late success or failure from the prior household/session/access context must not display its invitation, restore its code, or change the current screen's input, error, loading, copy-feedback, or success state. Never retry automatically.
- Store every successful result as one paired snapshot, conceptually `{ submittedEmail, invitationId, code, expiresAt }`. Normalize the email before submission using the same trim-and-lowercase rule as the backend, and save the exact normalized value sent with that response. Render the recipient text, ID (if shown), code, and formatted expiry only from this snapshot. Editing the form email must not relabel the existing invitation. A later validation or API failure—including `409`—must preserve the previous snapshot unchanged; replace the full snapshot only after a later request succeeds. Clear it only on route close/unmount or household/session/owner-access change.
- Hide the entry action for `member` memberships and guard the invitation screen against a missing/non-owner selected household. This is usability only: the server’s owner check remains the security boundary.
- Keep the paired invitation snapshot and its copy action available across temporary tab switches while this route remains mounted. While a subsequent valid request is pending, retain the previous snapshot; replace it only when the new request succeeds. On validation/API failure, keep its recipient, code, and expiry paired and available while showing the new error separately. Test that editing the email or a failed second request cannot relabel/destroy the only code the owner has.
- Map `422` to an email-format correction, `409` to the existing active-invitation explanation, and other/network failures to a safe retry message. Preserve server response bodies and codes out of UI/logs. Disable duplicate submissions while pending; do not add retries or alter backend conflict semantics.
- Call `Clipboard.setStringAsync(snapshot.code)` only after an explicit tap while the current route, household, authenticated session, and owner access still match the snapshot context. Show copy success only if the Promise resolves to `true`; treat `false` and rejection as visible copy failures. After a household/session/access/route change, suppress any late success/failure feedback and never let it update a newer screen state. A native clipboard write already dispatched cannot be revoked; the OS clipboard is allowed only as the result of that explicit user action.
- Format `expires_at` as a localized date/time while retaining the original timestamp for state. If the server returns an invalid timestamp, show a safe generic expiry label and report the API contract issue only in tests/development diagnostics without including the invitation code or email.

## Documentation/version and clipboard decision

The current merged baseline resolves Expo `57.0.25`, React Native `0.86.3`, Expo Router `57.0.23`, Expo Symbols `57.0.3`, and Clerk Expo `4.6.5`. The SDK 57 patch-alignment work merged through PR #7; no native rebuild has yet been performed. The approved `expo-clipboard: ~57.0.2` resolves to `57.0.2`. The official [Expo SDK 57 Clipboard documentation](https://docs.expo.dev/versions/v57.0.0/sdk/clipboard/) lists recommended version `~57.0.2`, supports iOS, Android, and web, documents `Clipboard.setStringAsync()` for copying, and says the module is included in Expo Go. Expo Clipboard's SDK 57 options do not document Android's newer sensitive-clipboard option, so the implementation does not assume that option exists at this pinned version.

For a flow exercised in SDK-matched Expo Go, the module is already present in that host and does not by itself require a custom native rebuild. Any installable custom development/production binary must include the native module and therefore be rebuilt after adding the package. This repo still has no `expo-dev-client` dependency or `eas.json`; adding/configuring those or starting EAS builds is a separate approval. Local CNG (`expo prebuild` plus platform `expo run:*`) is available only with the corresponding native toolchain and explicit build approval. Do not initiate a build within this UI slice without approval.
